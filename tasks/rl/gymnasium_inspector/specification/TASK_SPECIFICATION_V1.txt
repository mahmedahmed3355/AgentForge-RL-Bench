AgentForge-RL-Bench
Gymnasium / Inspector
Canonical Task Specification v1

PURPOSE

This specification defines the canonical structure for all Gymnasium / Inspector reinforcement-learning benchmark tasks.

The specification is shared by all 33 tasks.

DIFFICULTY

The task family contains exactly three difficulty levels:

medium
hard
very_hard

Easy is excluded.

Target distribution:

11 medium tasks
11 hard tasks
11 very hard tasks

Total: 33 tasks

TASK ID FORMAT

Medium:
GI-M01 through GI-M11

Hard:
GI-H01 through GI-H11

Very Hard:
GI-VH01 through GI-VH11

PRIMARY CAPABILITY

Every task must declare one primary capability.

Supported capabilities include:

observation
state_reasoning
planning
action_selection
dependency_tracking
diagnosis
recovery
verification
persistence
optimization
tool_usage
generalization

Secondary capabilities may also be declared.

TASK DATA

Task data contains information legitimately available to the agent.

Task data may contain:

task_id
version
scenario_id
public_parameters
initial_state_parameters
resource_limits
timeout
seed
public_metadata
objective_description

Task data must not contain:

oracle_solution
hidden_solution
hidden_tests
verifier_secrets
evaluator_secrets
reference_trajectory
hidden_scenario_parameters
gold_answer

ENVIRONMENT

Every task must expose a deterministic environment contract.

Required operations:

reset
step
close

The environment must define:

initial_state
observation
action_validation
state_transition
reward
termination
truncation
info
reset_semantics

The environment must support:

seeded execution
deterministic replay
trajectory recording
failure handling
terminal verification
reset isolation

STATE

The environment state must be explicit and reproducible.

Typical state fields may include:

episode_step
logical_stage
current_phase
completed_milestones
objective_state
validation_state
performance_state
failure_state
failure_history
recovery_count
checkpoint_state
terminal_state
success_state

LOGICAL STAGES

Every task must define logical stages.

A typical task may contain:

observe
inspect
diagnose
act
validate
recover
final_verify

Logical stages are conceptual state phases and are not necessarily identical to individual agent actions.

ACTION CONTRACT

Every action must define:

action_name
arguments
preconditions
state_transition
postconditions
reward_effect
failure_behavior

Invalid actions must be handled deterministically.

Invalid actions must not create unintended progress.

INSPECTOR

The Inspector is an agent-facing information interface.

Inspector information must represent information legitimately observable by the agent.

Allowed information includes:

public state
public diagnostics
public event history
public progress
public environment observations

Forbidden information includes:

hidden state
oracle information
hidden tests
verifier secrets
evaluator secrets
hidden answers
private benchmark information

OBJECTIVE

Every task must define:

objective
success_conditions
failure_conditions
terminal_conditions

Optional:

recovery_conditions

Success must be independently verifiable.

REWARD

Reward may contain multiple components.

Possible components include:

progress
milestone
correctness
testing
recovery
performance
efficiency
terminal_success
penalties

Terminal success must dominate shaping reward.

Reward must correspond to the actual benchmark objective.

REWARD HACKING

Every task must be evaluated against possible reward exploitation.

The task design must consider:

reward_farming
repeated_cheap_actions
reset_farming
duplicate_submissions
partial_credit_loops
timeout_exploitation
stale_state_exploitation
verifier_manipulation
hidden_information_discovery
reward_manipulation

The genuine objective must remain more valuable than exploitation.

FAILURE MODES

Every task must define expected failure classes.

Possible classes include:

invalid_action
wrong_order
wrong_state
incorrect_configuration
timeout
failed_validation
dependency_violation
stale_state
incomplete_solution
recovery_failure

Failures should be observable and classifiable.

RECOVERY

If recovery is part of the task, define:

recoverable_failures
recovery_actions
recovery_preconditions
recovery_cost
recovery_reward
unrecoverable_terminal_states

Recovery must require meaningful reasoning.

ORACLE

Every task must contain a reference solution.

The oracle must prove:

the task is solvable
the environment behaves correctly
a valid trajectory exists
the terminal state is valid
the verifier accepts the solution
the reward is within the expected range

The oracle must not be available to the agent.

VERIFIER

The verifier is the source of truth.

The verifier must independently validate:

final_state
correctness
required_invariants
terminal_conditions
required_artifacts
performance_requirements_when_applicable

The verifier must not trust agent self-reported success.

EVALUATION

Tasks should support:

training scenarios
public evaluation scenarios
hidden evaluation scenarios

Hidden evaluation information must remain outside the agent-visible interface.

SCENARIO GENERATION

Every task must define:

scenario_id
seed
parameter_generation
training_distribution
evaluation_distribution
hidden_distribution
reproducibility_rules

Training and evaluation distributions must be separated.

DETERMINISM

Given the same:

task_version
scenario_id
seed
action_sequence

the environment should produce the same transition sequence.

This supports:

debugging
replay
benchmark_validation
trajectory_analysis
failure_reproduction

ANTI-CHEAT

Task design must consider:

filesystem inspection
environment inspection
process inspection
source inspection
hidden_path_discovery
oracle_discovery
verifier_discovery
answer_extraction
reward_manipulation

Only legitimate agent information may be exposed.

TRAIN EVAL SEPARATION

Training data must not contain hidden evaluation scenarios.

Evaluation scenarios must be isolated from training data.

Hidden evaluation information must not be recoverable from public metadata.

VALIDATION GATES

A task is not complete until all required validation gates pass.

Required gates:

package_import
configuration_validation
task_data_validation
task_generation
environment_reset
environment_step
environment_close
action_validation
reward_validation
verifier_validation
oracle_pass
deterministic_replay
reset_isolation
anti_cheat_validation
reward_hacking_validation
failure_validation
recovery_validation_when_applicable
hidden_evaluation_validation
no_op_baseline_failure
trajectory_validation
documentation_validation

TASK FREEZE

The canonical completion sequence is:

oracle validation
verifier validation
anti-cheat validation
reward-hacking validation
determinism validation
failure validation
recovery validation
difficulty calibration
final audit
task freeze

A task must not be considered production-ready before all applicable gates pass.
